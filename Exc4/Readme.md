# Задание 4. Проектирование продажи ОСАГО

## Реализация osago-aggregator.
 
- Сервис представляет из себя довольно глупый гейт до конкретных систем страховых компаний
- Принимает команду на формирование информации о заявке
- Формирует внутри себя список задач, необходимых для исполнения (каждая задача это обращение в конкретную страховую компанию)
- Так как расчет страховки это не самое типовое задание - смысла кешировать результаты обращений нет
- Задача, поставленная в очередь исполнения, хранится в БД сервиса 
- Отдельный поток из пула потоков выбирает задачу и ставить SELECT FOR UPDATE тем самым забронировав данную задачу для себя 
- При получении ответа от страховой публикуется событие "Ответ от страховой Х по заявке номер ХХ"
- Rate limitimg применяется на взаимодействии с АПИ страховой, чтобы учесть требования внешнего АПИ
- TimeOut используется для каждой задачи, указывая на то, что задача уже не нуждается в исполнении. Тут 2 сценария:
  - пользоватедь закрыл форму или уже выбрал нужную заявку, core-app публикует событие, что все задачи по заявке нужно прекратить выполнять
  - каждая задача в очереди задач osago-aggregator имеет expiredAt, когда ее выполнения уже никто не ждет, такие задачи где expiredAt>now() будут пропускаться, по ним публикуется событие о "протухании"

Таким образом весь процесс:

- Пользователь открывает форму заявки
- Выбирает все или конкретные страховые 
- Формирует запрос на заявку 
- Пользователь видит отдельные экраны по каждой страховой
- core-app обрабатывает данный запрос, формирует заявку, формирует команду, сложив ее в Transactional Outbox
- Поток из пула потоков выбирает команду для отправки, отправляет в kafka
- osago-aggregator получает команду, складывает себе в БД метаданные о команде, формирует в своей БД набор задач для исполнения
- Поток из пула потоков выбирает задачу, отправляет запрос к конкретной страховой. Если апи страховой компании предусматривает лимиты на взаимодействие, то используется rate limiting, позволяющий взять в работу следующую заявку, избежав потери времени на получение 429 ошибки от апи.
- Получив ответ о страховой, osago-aggregator публикует событие ответа от страховой
- core-app получает событие, отображает пользователю информацию о расчетах через server push механизм
- каждый экран отдельной страховой отображает информацию, если получено событие о "протухании", экран отображает заглушку "не получилось"
