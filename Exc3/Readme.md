# Задание 3. Переход на Event-Driven архитектуру

## Анализ текущих проблем

### Медленная обработка запросов к ins-product-aggregator:
Сервис запрашивает данные у всех страховых компаний в рамках синхронного запроса, что приводит к значительным задержкам.
С увеличением числа страховых компаний задержки будут расти.
### Дублирование данных о продуктах и тарифах:
Реплики данных хранятся в core-app и ins-comp-settlement, что увеличивает вероятность несогласованности данных.
Обновления производятся через REST API, что не гарантирует точности и своевременности данных при росте числа запросов.
### Медленная обработка запросов к core-app
Для формирования данных для взаиморасчетов синхронно запрашиваются данные из core-app, что может вести к непредсказуемым последствиям: 
 
- данные запрашиваются долго, что может выйти за рамки read timeout операции
- данных запрашивается много, что может привести к ООМ

## Предлагаемые решения

- Использование ins-product-aggregator как gate для получения информации о тарифах 
- Использование redis для хранения информации о тарифах и подключенных страховых компаниях
- Использование cron job для запроса информации о тарифах отдельно для каждой компании
- Использование библиотеки ins-product-aggregator-agent внутри других компонентов для доступа к данным в redis
- Использование event sourcing подхода для формирования информации о взаиморасчетах
- Использование kafka для реализации event sourcing как самого распространенного решения
- Использование паттерна Transactional Outbox при передаче событий о заключении страховки, чтобы процесс отправки события и процесс залючения договора вывести в разные транзакции
